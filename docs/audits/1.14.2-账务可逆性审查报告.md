## 结论

两个风险都已在原业务代码上复现，再以相同复现用例验证修复。最终 87 项测试通过，0 失败、0 错误、0 跳过。已有 62 项测试保留，并新增 25 项；迁移测试额外覆盖 v6→v7。

我建议将这份修复进入 1.14.2 合并审查。它能阻止重导悄悄恢复已删除流水，并让新建重复关联保存可撤销的退款归属。它不能推断 v6 已经丢失的历史归属，旧的含退款关联采取拒绝不安全撤销的策略。

本轮未修改正式用户数据库，未执行 APK assemble/发布，未修改应用版本号或签名，未推送或合并 main。只在本机独立分支和合成测试数据库中工作。

## 只读追踪与根因

已读取 TransactionRepository、DuplicateMatching、TransactionDao、LedgerMetaDao、交易/导入批次/身份实体、AccountingIntegrityTest、LedgerRepositoryTest，以及关联的余额、迁移和备份代码。

| 生命周期环节 | 1.14.1 的实际行为 | 本次处理 |
|---|---|---|
| 导入 | 先检查 importKey，包括已删除行；非空批次会触发特殊恢复分支 | 命中删除标记直接跳过，原记录不改 |
| 待核对 | reviewReason 不为空时排除统计和余额 | 保留口径 |
| 重复关联 | 选择主记录；把辅助记录的退款移到主记录，并同步分类 | 同事务保存前后关系，仅保存被改动字段及关联标记 |
| 编辑 | 已有重复证据限制金额/类型修改，原消费分类会同步退款 | 保留原编辑规则；撤销前核对关系是否已被再次改动 |
| 删除 | 软删除；受活跃退款/辅助证据约束 | 保留；重导不能充当恢复操作 |
| 恢复 | 单笔恢复及指定批次恢复 | 保留显式恢复入口；退款原消费不能已成为辅助记录或改成收入 |
| 解除关联 | 原来只清 duplicateOfId，标记待核对，不恢复已移动的退款 | 有记录则校验并还原；无记录且涉及退款则拒绝猜测 |
| 再次导入 | 原来能清 deletedAt、改批次、重新匹配余额账户 | 不能复活删除行，也不能接管其批次 |

问题一在基准版本 `TransactionRepository.kt:457–469`：`exact.deletedAt != null && batchId != null` 后，直接 `copy(deletedAt = null, importBatchId = batchId, balanceAccountId = ...)`。因此必须传入真实导入流程使用的批次才能复现；不带批次的测试不会触发这个恢复分支。

问题二在基准版本 `TransactionRepository.kt:394–414`：linkDuplicate 把 secondaryReturns 的 relatedTransactionId 改成 primary.id，却没有保存旧归属。unlinkDuplicate 只改辅助记录自身，并未逆向处理退款。退款证据合并还可能把主记录原来的退款类型和分类覆盖掉，同样需要记录撤销信息。

DuplicateMatching 本身只识别候选，并不自动合并。此次没有修改匹配条件，也没有添加“金额相同就自动合并”的行为。

## 修复方案与文件

- 导入保护：[TransactionRepository.kt:514](../../app/src/main/java/com/bookkeeping/app/data/repository/TransactionRepository.kt#L514)。删除行命中同一身份后直接按已存在记录跳过，连方向补全也不对删除行执行。无新增流水时丢弃本次空批次；混合批次只包含真正新增的流水。
- 关联与撤销：[TransactionRepository.kt:374](../../app/src/main/java/com/bookkeeping/app/data/repository/TransactionRepository.kt#L374)、[TransactionRepository.kt:420](../../app/src/main/java/com/bookkeeping/app/data/repository/TransactionRepository.kt#L420)。为辅助记录保存标记；为被改写的主记录和退款保存关联前后 relatedTransactionId、relationKind、category。关联、撤销、写入或清除记录都走 writeLedger 的数据库事务。
- 撤销预检：[TransactionRepository.kt:458](../../app/src/main/java/com/bookkeeping/app/data/repository/TransactionRepository.kt#L458)。先构造即将生效的关系，检查父记录、方向和退款额度，再写入。关系或分类后续已改动时拒绝覆盖；后来产生的其他证据也会阻止撤销其依赖的信息，软删除不能绕过这项保护。
- 恢复保护：[TransactionRepository.kt:285](../../app/src/main/java/com/bookkeeping/app/data/repository/TransactionRepository.kt#L285)。拒绝把删除退款恢复到已成为辅助记录或已改成收入的原交易上。
- 新实体：[DuplicateLinkChangeEntity.kt:7](../../app/src/main/java/com/bookkeeping/app/data/local/entity/DuplicateLinkChangeEntity.kt#L7)。新增 duplicate_link_changes 表，以 secondaryId + transactionId 为主键。只保存关联操作改动的字段，保留后续合法的金额/备注编辑。
- DAO：[LedgerMetaDao.kt:17](../../app/src/main/java/com/bookkeeping/app/data/local/dao/LedgerMetaDao.kt#L17) 和 [TransactionDao.kt:73](../../app/src/main/java/com/bookkeeping/app/data/local/dao/TransactionDao.kt#L73)。提供撤销记录查询/写入、退款历史和证据依赖查询。
- 迁移：[BookkeepingDatabase.kt:41](../../app/src/main/java/com/bookkeeping/app/data/local/BookkeepingDatabase.kt#L41)，以及 DatabaseModule、schema 7.json。仅加表，不改写 v6 任何业务行或旧表结构；没有破坏性迁移或降级删除。
- 备份：[LedgerBackup.kt:88](../../app/src/main/java/com/bookkeeping/app/data/backup/LedgerBackup.kt#L88)、[LedgerBackup.kt:205](../../app/src/main/java/com/bookkeeping/app/data/backup/LedgerBackup.kt#L205)。新备份格式为 format 3 / databaseVersion 7，包含撤销记录。恢复时与流水同事务替换；仍可读 format 1 / DB5 与 format 2 / DB6 测试样本。新格式缺少撤销分区时在写入前拒绝。
- UI 提示：TransactionViewModel 的解除重复关联失败消息说明可能缺少旧归属或已发生后续修改。没有改动其他页面。
- 测试配置：app/build.gradle.kts 仅增加已提交 schema 的测试资源路径，供真实 v6 schema 创建迁移夹具；应用版本、依赖版本、签名没有改变。

accountingPeriod、余额加减公式、DuplicateMatching 和统计 SQL 未改动。解除关联后辅助记录仍按既有规则进入待核对，用户确认独立后才重新计入；两个复现测试分别检查了解除时的归属与确认后的统计。

## 旧数据兼容性与剩余风险

1. v6 原表、字段和全部夹具数据不变，v7 只加空撤销记录表。v1～v6 均有向 v7 的迁移覆盖。
2. 旧版重导已经复活的流水，无法自动判定用户之前是否主动删除；本次不批量重删，不改生产账本。
3. v6 已丢失的退款旧归属无法重建。旧关联含退款或报销历史时拒绝猜测性撤销；无相关历史的普通旧关联仍可解除。需要用户依据原始账单人工核对。
4. 新关联之后若关系/分类被再次修改，或其他证据依赖已改写字段，自动撤销会被拦住。当前实现没有自动解决这类冲突的 UI 向导。
5. v3 新备份不能由 1.14.1 旧版读取；不提供 v7→v6 数据库降级。发布前应保留升级前外部备份。
6. 故障注入验证的是 SQLite 异常导致事务回滚，不等于真机断电、进程强杀、磁盘满和文件系统损坏测试。尚未用 K80 Pro 上的 v6 账本副本覆盖升级。
7. 两个复现是仓储层合成流水，不代表重新验证了全部银行 PDF、微信或支付宝文件模板，也没有逐笔修复真实历史账本。
8. 批次恢复仍沿用 deletedAt 时间戳识别本批撤销行；主动删除与批次撤销同毫秒重合等情况未专项验证。本轮不宣称解决所有历史删除来源歧义。
